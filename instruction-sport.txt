Usa il connettore GitHub autorizzato e fonti web/API pubbliche. Fuso operativo: `Europe/Rome`.

SCHEMA DA RISPETTARE
La root deve contenere esattamente, in quest'ordine:
`lastModifiedDate`, `timezone`, `games`, `sport`, `eventi`.

La sezione di competenza deve avere esclusivamente:
{
  "lastModifiedDate": "<UTC ISO-8601>",
  "items": [
    {
      "title": "<titolo>",
      "subtitle": "<data italiana>",
      "dateTime": "YYYY-MM-DDTHH:mm",
      "text": "<descrizione>",
      "logo": "BA|ITA|F1",
      "link": "<Google Calendar>",
      "linkDettagliEvento": "<URL opzionale>"
    }
  ]
}

Non aggiungere `status`, `title` o `period` al livello della sezione. Ogni item deve invece contenere obbligatoriamente tutti i campi indicati, incluso `dateTime`; `linkDettagliEvento` resta l'unico campo facoltativo.

GATE OBBLIGATORIO DATETIME PRIMA DEL WRITE
1. Durante la creazione di ogni item valorizza subito `dateTime`; non aggiungerlo in un secondo momento facoltativo.
2. Costruisci `dateTime` dalla data locale dell'evento in `Europe/Rome` nel formato esatto `YYYY-MM-DDTHH:mm`.
3. Se l'orario è noto usa l'ora locale confermata. Se non è noto usa sempre `00:00`.
4. Prima di serializzare il JSON, scorri nuovamente tutti gli item di `sport.items`. Se `dateTime` manca, è `null`, è vuoto o ha formato errato, ricostruiscilo immediatamente dalla data dell'evento e dall'orario usato in `subtitle`.
5. Conta gli item senza `dateTime` valido: il risultato deve essere esattamente `0`.
6. Non chiamare `update_file` con item privi di `dateTime`. Questo controllo non deve bloccare l'aggiornamento: correggi gli item e prosegui con il commit.
7. Verifica il payload JSON finale già serializzato, non soltanto gli oggetti temporanei usati durante la ricerca.

PROTEZIONE DELLE ALTRE SEZIONI
1. Come prima operazione leggi da GitHub `dashboard.json` su `main`, verifica che sia JSON valido e acquisisci la blob SHA.
2. I dati già presenti in `sport.items` sono obsoleti: non usarli come fonte e ricostruisci l'array completo.
3. Non modificare mai `games`, `eventi`, `timezone` o le loro `lastModifiedDate`.
4. Subito prima del salvataggio rileggi file e SHA. Inserisci la nuova sezione `sport` nell'ultima versione disponibile, preservando integralmente le altre sezioni.
5. Imposta allo stesso istante UTC ISO-8601 sia la `lastModifiedDate` root sia `sport.lastModifiedDate`.

INTERVALLO
Calcola una sola volta l'intervallo da oggi a oggi + 14 giorni inclusi in `Europe/Rome`. Non pubblicare eventi fuori intervallo. L'intervallo non va scritto nel JSON.

SPORT DA INCLUDERE
- SSC Bari: tutte le partite ufficiali nel periodo.
- Nazionale italiana maschile senior: tutte le gare ufficiali e amichevoli nel periodo.
- Formula 1: tutte le sessioni ufficiali del weekend nel periodo, secondo il formato effettivo: FP1, FP2, FP3, Sprint Qualifying, Sprint, Qualifiche e Gara.

Non inserire eventi territoriali, concerti, sagre o altri sport.

FLUSSO DI RICERCA RAPIDO
1. Consulta una fonte ufficiale per ciascun ambito: calendario SSC Bari/competizione, FIGC/UEFA/FIFA e Formula 1.
2. Usa una seconda fonte solo per risolvere date, orari o formato discordanti.
3. Recupera insieme tutte le gare/sessioni nell'intervallo; non eseguire una ricerca web separata per ogni item.
4. Converti gli orari in `Europe/Rome` una sola volta, considerando ora legale/solare e distinguendo correttamente ora locale e UTC.

CAMPI ESATTI DI OGNI ITEM
`title`, `subtitle`, `dateTime`, `text`, `logo`, `link`; `linkDettagliEvento` è facoltativo.

Vietati campi aggiuntivi come `date`, `startTime`, `location`, `category` o `logoURL`. `dateTime` è l'unico campo tecnico ammesso per data e ora.

REGOLE DEI CAMPI
- `title`: titolo breve della partita o sessione.
- `subtitle`: data italiana, ad esempio `Venerdì 30 ottobre • 19:30`; ometti l'ora soltanto se non verificabile.
- `dateTime`: obbligatorio, mai `null`, formato locale ordinabile `YYYY-MM-DDTHH:mm` in `Europe/Rome`, ad esempio `2026-10-30T19:30`. Usa l'orario confermato; se l'orario non è disponibile usa obbligatoriamente `00:00`. Non aggiungere secondi o offset UTC.
- `text`: calcio `Competizione • Partita`; Formula 1 `Formula 1 • GP ... • Sessione`.
- `logo`: esclusivamente `BA`, `ITA` o `F1`.
- `link`: sempre e soltanto un URL Google Calendar precompilato. Titolo = `title`, descrizione = `text`, luogo = stadio/circuito e città se verificati. Con ora certa crea un evento temporizzato con durata ragionevole; senza ora crea un all-day di un giorno. Converti correttamente Europe/Rome e UTC.
- `linkDettagliEvento`: URL HTTP/HTTPS specifico ufficiale o attendibile; omettilo se non verificabile.

Ordina gli item in ordine crescente usando direttamente `dateTime`. Gli eventi senza orario vengono quindi ordinati alle `00:00` del relativo giorno.

VALIDAZIONE
- JSON parseabile e leggibile con indentazione.
- Root e schema esatti.
- Solo logo `BA`, `ITA`, `F1`.
- Ogni item contiene un `dateTime` valido nel formato `YYYY-MM-DDTHH:mm`; se `subtitle` non contiene un orario, `dateTime` termina con `T00:00`.
- Nessun evento fuori dai 15 giorni inclusivi.
- Nessuna partita/sessione ufficiale mancante o duplicata.
- Link Calendar coerenti con data, ora, titolo e luogo.
- `games` ed `eventi` coincidono con l'ultima versione riletta prima del write.
- Se i risultati appaiono troncati o inaffidabili, non pubblicarli e segnala il problema.

Commit message esattamente:

Data e ora del commit in `Europe/Rome`, sempre a due cifre, senza altro testo.

Se il write ha esito incerto, rileggi prima il file: se `sport.lastModifiedDate` coincide con quella generata, non creare un secondo commit.

Dopo il write rileggi il file da GitHub e verifica JSON, schema, conteggio, timestamp e conservazione delle altre sezioni. Riferisci commit SHA ed esito della rilettura GitHub. Non verificare l'URL raw.
